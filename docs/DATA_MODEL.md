# Модель данных

Документ фиксирует договорённости спринта 2: какие данные сохраняются, в каком
виде, какие связи и ограничения действуют. Роль Product Owner согласовала
состав полей, роль Lead Developer — реализацию в Room.

## 1. Общая схема

```
┌─────────────────────────────┐          ┌──────────────────────────────────┐
│ disciplines                 │          │ grades                           │
├─────────────────────────────┤          ├──────────────────────────────────┤
│ id        INTEGER PK        │ 1      N │ id           INTEGER PK          │
│ name      TEXT UNIQUE       │◄─────────│ discipline_id INTEGER FK         │
│ teacher   TEXT NULL         │          │ value         INTEGER (2..5)     │
│ created_at INTEGER          │          │ date          TEXT (yyyy-MM-dd)  │
└─────────────────────────────┘          │ work_type     TEXT               │
                                         │ comment       TEXT NULL          │
                                         │ created_at    INTEGER            │
                                         └──────────────────────────────────┘
```

Одна дисциплина — много оценок. Оценка не может существовать без дисциплины.

## 2. Таблица `disciplines`

| Поле | Тип | Обязательное | Ограничения | Назначение |
|---|---|---|---|---|
| `id` | INTEGER | да | PRIMARY KEY AUTOINCREMENT | идентификатор |
| `name` | TEXT | да | UNIQUE, 2–60 символов (проверка в коде) | название предмета |
| `teacher` | TEXT | нет | до 60 символов | преподаватель |
| `created_at` | INTEGER | да | — | момент создания записи, мс |

Уникальность `name` — индекс `index_disciplines_name`. Дубликат названия
отклоняется базой (`SQLiteConstraintException`), а не только интерфейсом:
проверка не зависит от того, какой экран добавляет запись.

## 3. Таблица `grades`

| Поле | Тип | Обязательное | Ограничения | Назначение |
|---|---|---|---|---|
| `id` | INTEGER | да | PRIMARY KEY AUTOINCREMENT | идентификатор |
| `discipline_id` | INTEGER | да | FOREIGN KEY → `disciplines.id`, ON DELETE CASCADE | дисциплина |
| `value` | INTEGER | да | 2–5 (проверка в коде, раздел 4 ТЗ) | оценка |
| `date` | TEXT | да | ISO `yyyy-MM-dd` | дата выставления |
| `work_type` | TEXT | да | одно из `control`, `practice`, `lab`, `answer`, `other` | вид работы |
| `comment` | TEXT | нет | до 200 символов | комментарий |
| `created_at` | INTEGER | да | — | момент создания записи, мс |

Индексы: `index_grades_discipline_id` (выборка оценок дисциплины),
`index_grades_date` (фильтр по периоду).

## 4. Принятые решения и их причины

### 4.1. Дата строкой ISO, а не `Date`/`LocalDate`

* `yyyy-MM-dd` сортируется лексикографически так же, как хронологически —
  `ORDER BY date` и `BETWEEN` работают без конвертеров;
* не нужен `java.time` и core library desugaring на minSdk 24;
* значение читаемо в DB Browser и в `App Inspection`;
* формат проверяется один раз при записи (`GradeDate.isValid`).

Цена решения: невозможно «одним запросом» получить месяц/год без строковых
функций. Для фильтра по периоду это не нужно: границы периода передаются
строками ISO.

### 4.2. Каскадное удаление оценок

`ON DELETE CASCADE` выбран вместо запрета удаления непустой дисциплины.
Причина: оценка без дисциплины — «мусорная» запись, а блокировка удаления
заставляет пользователя удалять оценки вручную. Осознанность обеспечивается
интерфейсом: перед удалением дисциплины показывается подтверждение с числом
оценок (`GradeBookRepository.hasGrades`, `DisciplineDao.gradeCount`).

### 4.3. Вид работы — enum с кодом в БД

В базе лежит строковый код (`practice`), а не порядковый номер: данные
устойчивы к изменению порядка констант и читаемы. Неизвестный код
превращается в `OTHER` (`WorkType.fromCode`), приложение не падает.

### 4.4. Средний балл считается запросом, а не вручную

`AVG(value)` возвращает `NULL` для пустой выборки, поэтому запросы обёрнуты
в `COALESCE(..., 0.0)`: деления на ноль и `NaN` не возникает. Базовая версия
использует среднее арифметическое без весов (раздел 9 ТЗ); взвешенный балл
описан как усложнение и в спринт 2 не входит.

### 4.5. Схема экспортируется в репозиторий

`exportSchema = true`, каталог `app/schemas`. Файл `1.json` фиксирует первую
версию. При изменении полей версия увеличивается, рядом появляется `2.json`,
и пишется миграция — так изменения структуры видны в code review.

## 5. Поведение первого запуска и пустой базы

* Первый запуск: файл `gradebook.db` создаётся, таблицы и индексы — по схеме.
  После создания база пуста; класс `GradeBookApp` запускает `DemoData.seedIfEmpty`.
* `seedIfEmpty` проверяет `COUNT(*)` по дисциплинам: если база не пуста,
  ничего не добавляется. Дублирования при повторных запусках нет.
* После заполнения: 4 дисциплины, 10 оценок; «Физика» остаётся без оценок.
* Пустая база (если демо-данные удалены пользователем): списки пустые,
  средние баллы — `0.0`, интерфейс (спринт 3) показывает пустое состояние
  вместо нулевых строк.
* Удаление последней оценки не удаляет дисциплину: дисциплина с нулём оценок —
  корректное состояние, средний балл по ней не определён (в интерфейсе
  показывается прочерк, а не `0`).

| Дисциплина | Преподаватель | Оценки | Средний балл |
|---|---|---|---|
| Математический анализ | Смирнова О. В. | 5, 4, 3, 5 | 4.25 (контрольный пример ТЗ) |

| История | Волкова Е. С. | 3, 2, 4 | 3.00 |

Данные вымышленные: реальные персональные сведения в репозиторий не попадают.

## 7. Что появится в следующих спринтах

| Спринт | Изменения модели |
|---|---|
| 3 | без изменений схемы: экраны работают с готовыми DAO |
| 4 | агрегаты по периодам (средние по месяцам), сортировки, фильтры |

## 8. Как посмотреть базу

* Android Studio → View → Tool Windows → App Inspection → Database Inspector
  (приложение должно быть запущено на эмуляторе);
* файл базы на устройстве: `/data/data/com.example.edu_prac_3/databases/gradebook.db`;
* схема без запуска приложения: `app/schemas/com.example.edu_prac_3.data.local.AppDatabase/1.json`.
